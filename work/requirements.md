# Application requirements

## Scope and revision notes

Revision update: Metric keys use the exact format `MET-0001` with a hyphen and four digits. Metric placeholders use the exact syntax `[~MET-0001]`. The backend stores requirement descriptions unchanged, including valid metric placeholders, while read/export projections may additionally provide rendered text with resolved metric values. PDF export is not a current requirement; readable document exports target GitHub-flavored Markdown and AsciiDoc.

This file contains the complete application requirements catalogue for frontend and backend after revising the export requirements for all-project, project, and requirement-selection exports.

## Review workflow clarification

The review workflow applies to the frontend and backend and refines US-WF-002 through US-WF-005:

- Starting a review opens the review workspace but does not introduce an `in_review` requirement lifecycle status.
- A draft with at least one open main review comment is `in_review` for presentation purposes.
- A draft with main comments where every main comment is resolved is `decision_pending`.
- A draft without comments may still be approved explicitly when the reviewer name is supplied.
- Main comments can be resolved and remain visible with author, timestamps, resolution information, and replies.
- Replies are text-only discussion entries. They have no resolution status, cannot be replied to, and can only be added while their main comment is open.
- Requirements remain editable during review. Editing does not resolve comments automatically.
- Approval requires an explicit reviewer name and is blocked while any main comment is open.
- Rejection requires an explicit reviewer name and rejection reason. Rejection closes remaining open main comments with the distinct reason `requirement_rejected`, not `resolved`.
- Draft requirements in `in_review` or `decision_pending` open in the review workspace by default.
- Reviewer assignment and personal pending-review task lists remain requirements, but their implementation is deferred until authentication and a multiuser environment are introduced.

## Review user-interface clarification

- The action is labelled `Review`, not `Start review`, because opening the review workspace alone does not change review state.
- The requirement detail panel contains no local Edit button. Requirement actions are displayed in the route action bar.
- The detail action bar shows `Edit` for an editable requirement and additionally shows `Review` when the requirement status is `draft`.
- The review action bar shows `Edit`, `Approve`, and `Reject` only while the requirement status is `draft`.
- `Approve` and `Reject` disappear immediately after the requirement leaves `draft`.
- Opening a review route for an `approved`, `implemented`, `obsolete`, or `rejected` requirement redirects to its detail view.
- Rejected requirements are read-only. Their action bar does not show `Edit`.
- The rejected requirement detail view shows the reviewer, rejection reason, and rejection timestamp.
- There is no `Reopen` or implicit `rejected` to `draft` transition.

## Obsolescence workflow clarification

- Only requirements with status `approved` or `implemented` can be marked `obsolete`.
- Their action bar shows a button labelled exactly `Obsolete`.
- `Obsolete` opens the same reusable lifecycle confirmation dialog as approval and rejection. The user's name and an obsolescence reason are mandatory.
- Draft requirements are deleted or rejected instead of being marked obsolete.
- Rejected requirements remain rejected so that the rejection decision is preserved.
- The name of the user performing the action is stored in the dedicated `obsoletedBy` field; it does not overwrite the reviewer/approver.
- The obsolescence reason is stored in `obsolescenceReason`, and the server records `obsoleteAt`.
- Every obsolete transition creates the next requirement revision containing the obsolescence metadata.
- Obsolescence preserves the internal immutable ID, visible requirement key, revision history, and traceability information.
- Obsolete requirements cannot be deleted and remain available through explicit search, reporting, history, and export options.

## Implementation workflow and ticket traceability clarification

- An implementation ticket can be added only to a requirement with status `approved`.
- A requirement can reference one or more implementation tickets.
- Every implementation ticket stores a non-empty ticket ID, a non-empty `completedBy` name, and a ticket completion date in `completedAt`.
- Ticket IDs are unique within one requirement.
- Implementation tickets can be added, edited, and removed while the requirement remains `approved`.
- A project can configure one ticket URL template, for example `https://github.com/xxx/{ticket-id}`.
- The ticket URL template must contain the placeholder `{ticket-id}` exactly once and must produce an absolute `http` or `https` URL.
- Ticket URLs are derived by URL-encoding the ticket ID and substituting it for `{ticket-id}`; the derived URL is not stored redundantly with the ticket.
- Without a configured ticket URL template, ticket IDs remain visible as plain text.
- Implementation tickets and their clickable derived URLs are visible in requirement details for `approved`, `implemented`, and `obsolete` requirements.
- An `approved` requirement can be moved to `implemented` only when it has at least one complete implementation ticket.
- The action bar shows a button labelled exactly `Implemented` when the transition is allowed.
- `Implemented` changes the requirement status, not an individual ticket status, and the server records `implementedAt`.
- Implementation-ticket changes and the transition to `implemented` are retained in the requirement history.
- An `implemented` requirement is read-only. Its content, metadata, category, and implementation tickets cannot be changed.
- An `implemented` requirement cannot be deleted, rejected, reopened, or returned to `approved` or `draft`.
- The only permitted transition from `implemented` is to `obsolete`.
