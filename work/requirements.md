## Authentication and authorization clarification

- Authentication uses local accounts only. External identity providers, SSO, federation, and MFA are out of scope.
- Every user has an immutable, server-generated UUID. Relations and revision metadata use this UUID; username, email address, and display name are mutable attributes and never serve as technical identity.
- The username is the unique login identifier. A unique, verified email address is mandatory for password recovery.
- Normal registration creates a `pending` account. An Administrator must activate it and assign project memberships before application access is granted.
- Accounts are deactivated rather than physically deleted. Deactivation and password changes revoke all sessions, while historical user references remain valid.
- The four authorization roles are `Administrator`, `Requirements Engineer`, `Developer`, and `Viewer`. There are no separate Reviewer, Approver, Project Manager, or Tester roles.
- Story text may still use stakeholder personas such as Project Manager or Tester. These personas are not authorization roles unless a later requirement explicitly introduces them. Current authorization maps project creation, project deletion, project membership management, user administration, session administration, and project ticket-URL template management to the global Administrator role.
- Administrator is global, has global read access, and manages users, projects, memberships, project ticket-URL templates, and sessions. Administrator can create, rename, delete, and list all projects. Administrator does not mutate requirements, reviews, lifecycle state, or implementation tickets unless separately assigned a project role; normal Administrator accounts do not require project membership.
- Requirements Engineer, Developer, and Viewer are project-scoped membership roles. A user may hold different roles in different projects, and projects without membership are neither listed nor accessible.
- Requirements Engineer can create and edit requirements and implementation tickets, comment on and resolve reviews, and perform lifecycle transitions. Self-review is allowed.
- Developer can read project details and create, update, and remove implementation tickets while the requirement is `approved`; Developer cannot edit requirement content, review requirements, or change lifecycle state.
- Viewer has read-only access to all details of assigned projects, including rejected and obsolete requirements, reviews, implementation tickets, lifecycle metadata, revisions, and comparisons.
- The backend derives actor identity from the authenticated session. Client-supplied actor names are not trusted as authorization or history identities.
- The SPA keeps an opaque bearer session token only in JavaScript memory. Refreshing the page, closing the browser, or restarting it loses the token and requires login again.
- The backend stores only a hash of each session token and validates the corresponding server-side session on every authenticated request.
- A session expires after one hour without an authenticated request. There is no absolute lifetime while the session remains active.
- Logout, account deactivation, and password change revoke the affected sessions. An Administrator can revoke an individual session or all sessions of a user immediately.
- Passwords are hashed with Argon2id and are never stored in plaintext or reversibly encrypted. Authentication and recovery endpoints are rate-limited and use responses that do not disclose whether an account exists.
- Password reset uses a short-lived, single-use email token whose hash is stored server-side. Successful reset revokes every session of that user.
- If no Administrator has ever been created, the UI exposes initial-Administrator registration protected by a one-time deployment bootstrap secret. Creation is transactionally exclusive and permanently disables bootstrap. It does not reopen merely because all Administrators are later deactivated.

### Frontend shell and public account UI clarification

- Public account pages use a shared card-style layout for login, registration, password-reset request, password-reset confirmation, email verification, and bootstrap registration.
- Text inputs and password fields have internal horizontal padding so entered text does not touch the field border.
- Primary submit buttons have the application control height; loading indicators are centered horizontally and vertically in the button.
- The login page exposes only two account-help links below the submit button: `Do not have an account? Register yourself.` and `Forgot your password? Reset it here.` Each link is displayed on its own line. Resending verification email is handled only by the dedicated resend-verification page.
- The authenticated application shell exposes account actions through a cog-wheel menu on the right side of the action bar. The menu header displays the current display name and username. `Administration` is visible only for Administrators; `Logout` is visible for every signed-in user.
- Interactive navigation and menu rows use the same systemwide hover background token so hover feedback is visually consistent across the sidebar and account dropdown.

### Email-verification clarification

- Registration creates a 256-bit random verification token that expires after 30 minutes; only its SHA-256 hash is stored.
- The plaintext token is sent only through configured SMTP delivery and is never returned by the API.
- `POST /auth/email-verification/confirm` consumes a valid token once and records `emailVerifiedAt`; the account remains `pending` until Administrator activation.
- Invalid, expired, consumed, invalidated, and unknown tokens return the same generic invalid-link response.
- `POST /auth/email-verification/resend` always returns the same generic accepted response, regardless of account existence or eligibility.
- Resend is limited to one token per minute and five per rolling hour per account. A replacement invalidates prior unused tokens.
- SMTP and the frontend verification-link base URL are deployment configuration. External mail delivery is disabled in automated tests.
- SMTP failure does not remove the pending account or persisted token and is not disclosed publicly.

### Initial-Administrator bootstrap clarification

- `GET /auth/bootstrap/status` exposes only whether initial Administrator registration remains available.
- `POST /auth/bootstrap/administrator` requires the deployment-provided `INITIAL_ADMIN_BOOTSTRAP_SECRET`, applies normal account validation, and uses a generic failure message for missing and incorrect secrets.
- The initial user, global Administrator role, permanent bootstrap marker, and email-verification token are created in one database transaction. Concurrent requests can produce only one completed bootstrap.
- The initial Administrator is created as `pending`. Confirming that account's verification token changes it to `active`; verifying a normal account does not activate it.
- Bootstrap completion is permanent and does not depend on the Administrator's later account status. Deactivation cannot reopen registration.
- Attempts are rate-limited per hashed request source. Secrets, tokens, hashes, and account-existence information are never returned.
- Global Administrator assignment is separate from project memberships. Project-scoped roles and authorization are introduced later.

## Revision model clarification

- A freshly created requirement is revision 1. The current revision is stored in the `requirements` table; no duplicate revision-1 row is created in an archive table.
- When revision N changes, its complete pre-change snapshot is inserted into `requirement_revisions`, and the `requirements` row becomes revision N+1. The archive therefore contains predecessors while the requirement row contains the current revision.
- Archiving revision N preserves the revision metadata that already belongs to N. The change type, reason, actor, and timestamp for the operation being performed are applied to the new current revision N+1; they must not overwrite the metadata of archived revision N.
- Revision metadata is stored directly on both the current requirement and archived revisions: revision number, change type, non-empty change reason, `changedAt`, immutable `changedByUserId`, and a `changedByDisplayName` snapshot.
- Content changes, category changes, owner changes, implementation-ticket creation/update/removal, and every lifecycle transition to `approved`, `implemented`, `rejected`, or `obsolete` create a new revision.
- Direct edits of approved requirements temporarily use `changeType = content_changed`; US-VER-003 and US-VER-004 will later replace this with a controlled change-request workflow.
- Review comments, replies, and review-comment resolution do not create requirement revisions. Implementation-ticket creation, update, and removal create requirement revisions because they change the implementation state of the requirement.
- Requirement deletion, soft deletion, recycle-bin restoration, and reopen operations do not exist. A draft may be approved or rejected.
- Every revision has a non-empty immutable `changeReason`. Substantive requirement content, metadata, owner, or category edits require an explicit short reason from the authenticated user. Creation, approval, implementation, rejection, obsolescence, and implementation-ticket operations use deterministic server-derived reasons; rejection and obsolescence reasons incorporate the mandatory lifecycle reason supplied by the user.
- Revision history returns revisions `1..N`, including the current revision, ordered by revision number through `GET /projects/{projectId}/requirements/{requirementId}/revisions`.
- Comparison uses `GET /projects/{projectId}/requirements/{requirementId}/revisions/compare?from={fromRevision}&to={toRevision}` and compares requirement snapshot fields, including implementation-ticket snapshots, while excluding external audit-event data.
- Revision records are immutable. A general audit-event or audit-log subsystem is not required.

## Review workflow clarification

The review workflow applies to the frontend and backend and refines US-WF-002 through US-WF-005:

- Starting a review opens the review workspace but does not introduce an `in_review` requirement lifecycle status.
- A draft with at least one open main review comment is `in_review` for presentation purposes.
- A draft with main comments where every main comment is resolved is `decision_pending`.
- A draft without comments may still be approved explicitly by an authenticated Requirements Engineer.
- Main comments can be resolved and remain visible with author, timestamps, resolution information, and replies.
- Replies are text-only discussion entries. They have no resolution status, cannot be replied to, and can only be added while their main comment is open.
- Requirements remain editable during review. Editing does not resolve comments automatically.
- Approval uses the authenticated Requirements Engineer as actor and is blocked while any main comment is open.
- Rejection uses the authenticated Requirements Engineer as actor and requires a rejection reason. Rejection closes remaining open main comments with the distinct reason `requirement_rejected`, not `resolved`.
- Draft requirements in `in_review` or `decision_pending` open in the review workspace by default.
- Requirements Engineer assignment and personal pending-review task lists remain requirements but are not yet implemented, despite authentication and project memberships now existing.

## Review user-interface clarification

- The action is labelled `Review`, not `Start review`, because opening the review workspace alone does not change review state.
- The requirement detail panel contains no local Edit button. Requirement actions are displayed in the route action bar.
- The detail action bar shows `Edit` for an editable requirement and additionally shows `Review` when the requirement status is `draft`.
- The review action bar shows `Edit`, `Approve`, and `Reject` only while the requirement status is `draft`.
- `Approve` and `Reject` disappear immediately after the requirement leaves `draft`.
- Opening a review route for an `approved`, `implemented`, `obsolete`, or `rejected` requirement redirects to its detail view.
- Rejected requirements are read-only. Their action bar does not show `Edit`.
- The rejected requirement detail view shows the authenticated Requirements Engineer who rejected it, the rejection reason, and the rejection timestamp.
- There is no `Reopen` or implicit `rejected` to `draft` transition.

## Obsolescence workflow clarification

- Requirements with status `approved` or `implemented` can be marked `obsolete`. Draft requirements cannot be marked obsolete; they can only be approved or rejected.
- Their action bar shows a button labelled exactly `Obsolete`.
- `Obsolete` opens the same reusable lifecycle confirmation dialog as approval and rejection. The authenticated actor is derived by the backend and an obsolescence reason is mandatory.
- Draft requirements can be approved or rejected, but cannot be marked obsolete; requirement deletion is not available.
- Rejected requirements remain rejected so that the rejection decision is preserved.
- The authenticated actor is stored in dedicated obsolescence attribution fields; it does not overwrite prior review or approval attribution.
- The obsolescence reason is stored in `obsolescenceReason`, and the server records `obsoleteAt`.
- Every obsolete transition creates the next requirement revision containing the obsolescence metadata.
- Obsolescence preserves the internal immutable ID, visible requirement key, revision history, and traceability information.
- Obsolete requirements cannot be deleted and remain available through explicit search, reporting, history, and export options.

## Implementation workflow and ticket traceability clarification

- An implementation ticket can be added only to a requirement with status `approved`.
- A requirement can reference one or more implementation tickets.
- Every implementation ticket stores a non-empty ticket ID, a non-empty `completedBy` name, and a ticket completion date in `completedAt`.
- Ticket IDs are unique within one requirement.
- Implementation tickets can be added, edited, and removed while the requirement remains `approved`.
- A project can configure one ticket URL template, for example `https://github.com/xxx/{ticket-id}`.
- The ticket URL template must contain the placeholder `{ticket-id}` exactly once and must produce an absolute `http` or `https` URL.
- Ticket URLs are derived by URL-encoding the ticket ID and substituting it for `{ticket-id}`; the derived URL is not stored redundantly with the ticket.
- Without a configured ticket URL template, ticket IDs remain visible as plain text.
- Implementation tickets and their clickable derived URLs are visible in requirement details for `approved`, `implemented`, and `obsolete` requirements.
- An `approved` requirement can be moved to `implemented` only when it has at least one complete implementation ticket.
- The action bar shows a button labelled exactly `Implemented` when the transition is allowed.
- `Implemented` changes the requirement status, not an individual ticket status, and the server records `implementedAt`.
- The transition to `implemented` creates a requirement revision. Implementation-ticket changes create requirement revisions and ticket snapshots are included in revision history/comparison.
- An `implemented` requirement is read-only. Its content, metadata, category, and implementation tickets cannot be changed.
- An `implemented` requirement cannot be deleted, rejected, reopened, or returned to `approved` or `draft`.
- The only permitted transition from `implemented` is to `obsolete`.
