# Backend backlog: current not fully covered requirements

## Authentication and revision decisions

Authentication is the mandatory first stage of US-VER-002 because revision attribution requires a trusted, immutable actor. The application will use local accounts only. Each account receives an immutable server-generated UUID; username is the unique login identifier; a unique verified email address supports password recovery; and normal registration creates a pending account that an Administrator must activate and assign to projects.

The role model consists of global `Administrator` plus project-scoped `Requirements Engineer`, `Developer`, and `Viewer`. Administrator has global read access and administration-only mutation rights. Requirements Engineer manages requirements, reviews, lifecycle transitions, and tickets in assigned projects and may self-review. Developer manages implementation tickets for approved requirements in assigned projects. Viewer is read-only. No Reviewer or Approver role exists.

The SPA stores an opaque bearer token only in memory, so refresh and browser restart require login. Server-side hashed sessions expire after one hour without an authenticated request, have no absolute lifetime, and can be revoked by an Administrator. Local passwords use Argon2id. Password recovery uses verified email and short-lived single-use reset tokens. MFA, SSO, external identity providers, general audit events, and authentication-configuration history are out of scope. The first Administrator is registered through the UI using a one-time deployment bootstrap secret.

The revision model stores the current revision in `requirements` and archives its complete predecessor in `requirement_revisions` before each new revision. Revision 1 exists only as the initial current requirement until changed. Content, category, owner, and every lifecycle transition create revisions. Tickets and review activity do not create revisions and tickets are excluded from comparison. Requirements cannot be deleted, soft-deleted, restored, or reopened; a draft may be rejected or marked obsolete. History returns archived plus current revisions `1..N`; comparison uses the project-scoped `/revisions/compare` endpoint.

### Authentication work package 1 implementation update

The local-account foundation is implemented: immutable UUID users, case-insensitive normalized username/email uniqueness, `pending`/`active`/`deactivated` status, Argon2id password hashing, generic `202` pending registration, and internal activation/deactivation/password-hash service operations.

### Authentication work package 2 implementation update

Email verification is implemented with hashed 256-bit, 30-minute, single-use tokens; configurable SMTP delivery; generic confirmation failures and resend responses; database-backed resend limits; and pending-account retention after verification. Administrator activation, login, sessions, password reset, roles, memberships, endpoint authorization, and first-Administrator bootstrap remain open.

### Authentication work package 3 implementation update

The backend now provides transactionally exclusive first-Administrator bootstrap with a deployment secret, persistent completion marker, global Administrator role assignment, rate-limited attempts, generic secret failures, and status discovery. The initial account becomes active only after email verification; later deactivation cannot reopen bootstrap. A server-side emergency recovery command and the frontend bootstrap UI remain follow-up work.

### Authentication work packages 4 and 5 implementation update

The backend now supports username/password login with generic failures and database-backed rate limiting, hashed opaque server sessions, authenticated-user lookup, logout, and a one-hour inactivity timeout refreshed by every authenticated request. Administrator-protected APIs list users and their sessions, activate verified accounts, deactivate accounts, and revoke one or all sessions. Deactivation and password changes revoke every active session. SPA memory-only token storage remains a frontend responsibility; project memberships, project roles, endpoint permission enforcement, password-reset endpoints, and global-role management remain follow-up packages.

### Authentication work packages 6 through 8 implementation update

The backend now persists project-scoped Requirements Engineer, Developer, and Viewer memberships and provides Administrator-only membership APIs. Project endpoints enforce authentication, global Administrator read/project-administration rights, and project-scoped mutation permissions; lifecycle, review, and ticket actor display names are derived from the authenticated account. Password recovery uses non-enumerating, rate-limited requests, hashed 30-minute single-use tokens, Argon2id replacement hashes, and complete session revocation. An explicit server-side Administrator recovery command is available after initial bootstrap. Frontend memory-only session handling and revision actor UUID persistence remain in their respective frontend and revision packages.

## Review workflow implementation update

The review package now covers persistent main comments, resolving comments, text-only replies to open main comments, derived review summaries (`not_started`, `in_review`, `decision_pending`), approval without mandatory comments, approval blocking for open comments, and rejection with automatic `requirement_rejected` closure. Requirements Engineer assignment, authenticated authorization, and user-specific pending-task lists remain follow-up work. The detailed percentages below supersede older pre-review descriptions where applicable.

## Requirement lifecycle UI update

Rejected requirements are read-only and show actor, rejection reason, and timestamp. No reopen action exists. Draft, approved, and implemented requirements may be marked `Obsolete`; rejected and obsolete requirements may not. The authenticated actor is derived by the backend, `obsolescenceReason` is required, `obsoleteAt` is server-generated, and the transition creates a revision. No requirement deletion remains in the product.

## Implementation-ticket workflow update

The implementation-ticket package is covered. Approved requirements support multiple validated tickets containing ticket ID, `completedBy`, and `completedAt`; a project-scoped `{ticket-id}` URL template derives clickable links; and the guarded `Implemented` action requires at least one ticket. Implemented requirements and tickets are read-only and may only proceed to `obsolete`. Ticket changes do not create requirement revisions, ticket snapshots are not archived, and tickets are excluded from revision comparison.

## Scope

This backlog is based on static source-code inspection of the current uploaded backend after the requirement-link stabilization package and the GitHub-flavored Markdown / AsciiDoc export adapter package. Fully covered requirements are omitted.

PDF is kept as an unresolved backlog clarification: older acceptance criteria mention Markdown/PDF exports, but the revised `US-EXP-*` adapter catalogue defines JSON, GitHub-flavored Markdown, AsciiDoc, YAML, and XML only; there is no dedicated PDF adapter story yet.

## Recommended next backend work packages

### Stage 1: Local authentication and authorization

**Included stories:** US-SEC-001, US-SEC-002, and US-SEC-004 through US-SEC-012.

**Scope:** immutable users, pending registration and activation, verified-email recovery, Argon2id login, memory-only opaque bearer sessions, one-hour inactivity expiry, session revocation, secure first-Administrator bootstrap, project memberships, and backend-enforced permissions.

**Definition of done:**

- All protected endpoints derive the user UUID from a valid server-side session.
- Administrator has global read and administration-only mutation access.
- Requirements Engineer, Developer, and Viewer permissions are enforced per project.
- Refreshing the SPA requires login again; inactive and revoked sessions are rejected.
- Registration, activation, password reset, first-admin bootstrap, and authorization boundaries have unit and E2E coverage.

### Stage 2: Final revision storage and history

**Included stories:** US-VER-001 and stage 2 of US-VER-002.

**Scope:** current requirement plus archived predecessors, immutable actor UUID metadata, display-name snapshots, mandatory change reasons, revision creation for content/category/owner/lifecycle changes, clean history endpoint, and removal of deletion paths.

### Stage 3: Revision comparison

**Included stories:** stage 3 of US-VER-002.

**Scope:** project-scoped comparison endpoint and frontend diff view for requirement snapshots. Implementation tickets remain current-only data and are excluded from comparisons.

## Open catalogue clarification

- **PDF export:** US-IO-004, US-MET-018, and US-REF-016 still mention PDF, but the current `US-EXP-*` adapter list has no PDF story. Keep PDF in the backlog until the catalogue either adds a dedicated PDF adapter story or explicitly defines PDF as generated downstream from Markdown/AsciiDoc.
