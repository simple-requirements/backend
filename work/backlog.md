# Backend backlog: current not fully covered requirements

## Review workflow implementation update

The review package now covers persistent main comments, resolving comments, text-only replies to open main comments, derived review summaries (`not_started`, `in_review`, `decision_pending`), approval without mandatory comments, approval blocking for open comments, and rejection with automatic `requirement_rejected` closure. Reviewer assignment, authenticated authorization, and user-specific pending-task lists remain follow-up work. The detailed percentages below supersede older pre-review descriptions where applicable.

## Requirement lifecycle UI update

Rejected requirements are read-only in the frontend and their detail view shows reviewer, rejection reason, and rejection timestamp. No reopen action or implicit `rejected` to `draft` transition is planned. Approved and implemented requirements expose an `Obsolete` action that uses the shared lifecycle dialog and requires both the user's name and a reason; draft, rejected, and already obsolete requirements do not expose this action. Obsolescence stores the actor separately as `obsoletedBy`, preserves the reviewer/approver, stores `obsolescenceReason`, and records `obsoleteAt` on the server and in revision history.

## Implementation-ticket workflow update

The implementation-ticket package is now covered. Approved requirements support multiple validated tickets containing ticket ID, `completedBy`, and `completedAt`; a project-scoped `{ticket-id}` URL template derives clickable links; and the guarded `Implemented` action requires at least one ticket. Implemented requirements and tickets are read-only and may only proceed to `obsolete`. Ticket state is retained in requirement revision history.

## Scope

This backlog is based on static source-code inspection of the current uploaded backend after the requirement-link stabilization package and the GitHub-flavored Markdown / AsciiDoc export adapter package. Fully covered requirements are omitted.

PDF is kept as an unresolved backlog clarification: older acceptance criteria mention Markdown/PDF exports, but the revised `US-EXP-*` adapter catalogue defines JSON, GitHub-flavored Markdown, AsciiDoc, YAML, and XML only; there is no dedicated PDF adapter story yet.

## Recommended next backend work package

### Work package: Metric grammar and usage hardening

**Included stories:** US-MET-003, US-MET-007, US-MET-008, US-MET-010, US-MET-011, US-MET-013, US-MET-019, and the API part of US-MET-023.

**Goal:** Align metric references with the catalogue’s generic `[~KEY]` syntax and add the missing backend usage lookups so metrics can be searched, opened, and analyzed reliably.

**Scope:**

- Decide and implement the exact metric-key grammar so examples such as `MET001`, `MET002`, and `MAX_LATENCY` are either accepted or the requirement catalogue is corrected.
- Update metric creation validation, inline parsing, requirement validation, rendering, export warnings, and tests to use the same grammar.
- Add a metric usage endpoint that lists referencing requirements with visible key, derived type, category, status, and rendered text.
- Add requirement filtering/search by referenced metric key.
- Keep project scoping strict: a requirement may only reference metrics from the same project.

**Definition of done:**

- Metric key validation, inline parsing, rendering, and export diagnostics all use the same grammar.
- Requirements can be searched/filtered by referenced metric.
- Metric detail/usage API exposes referencing requirements and a usage count.
- Unit tests and API tests cover valid keys, invalid keys, unresolved references, duplicate references, same-project references, cross-project rejection, usage listing, and export behavior.

- **PDF export:** US-IO-004, US-MET-018, and US-REF-016 still mention PDF, but the current `US-EXP-*` adapter list has no PDF story. Keep PDF in the backlog until the catalogue either adds a dedicated PDF adapter story or explicitly defines PDF as generated downstream from Markdown/AsciiDoc.
